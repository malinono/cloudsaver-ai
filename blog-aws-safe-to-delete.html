How to Tell Whether an AWS Resource Is Actually Safe to Delete

Finding wasted AWS resources is easy. The hard part is knowing what you can actually remove without breaking something. Here's the framework I use.

← Back to CloudSaver (free AWS waste scanner)

I used to manage cloud accounts at a company.

One thing that always bothered me was how easy it was to keep paying for things nobody really needed anymore.

It wasn't usually one huge mistake.

It was a lot of small ones:

  • A temporary service that kept running after the project ended.
  • Snapshots or backups that were no longer needed.
  • A data volume that was still being charged after the original instance was gone.
  • A stopped EC2 instance where the instance charge had ended, but the attached storage was still costing money.
  • A public IPv4 address or another resource that nobody remembered to clean up.

Each item might look small.

But small charges that nobody owns can stay there for a long time.

That was part of why I started building CloudSaver.

But the more I worked on it, the more I realized that finding something expensive is usually not the hardest part.

The harder question is:

Can I safely remove it?

That's a different problem.

"Should delete" and "safe to delete" are not the same thing

A resource can look unused and still be important.

A snapshot might look like storage waste, but it could be the only rollback point for a system.

A data volume might be attached to something that is no longer obvious from the console, but is still referenced by an old process or recovery workflow.

And an "idle" instance may not be costing instance runtime anymore once it is stopped, while its attached EBS volumes or other billable resources can continue to incur charges. AWS also charges for public IPv4 addresses, so the surrounding resources matter too. AWS EC2 documentation

So I don't think the goal should be:

Find waste and delete it.

A better goal is:

Find waste, understand the dependencies, and remove only what you can explain and recover from.

I use four questions before deleting something

Question 1

Can I rebuild it from code or configuration?

If the answer is yes, that's a good sign.

If the answer is no, slow down.

Before deleting something that contains unique state, I want to know what the recovery path is.

Question 2

What still depends on it?

This is the question that gets missed most often.

Don't just look at the resource itself.

Look for:

  • applications
  • scripts
  • automation
  • backup jobs
  • network dependencies
  • recovery procedures

A resource can look isolated and still be part of a larger workflow.

Question 3

If something goes wrong, can I recover?

A cheap resource can become expensive very quickly if deleting it creates an outage or destroys the only recovery path.

Before deleting, I want to know:

  • what the rollback plan is
  • what backup exists
  • how long recovery would take
  • who would notice if the resource disappeared
Question 4

What evidence says nobody is using it?

"Nobody knows what this is" is not the same as "nobody uses it."

Better evidence includes:

  • usage data
  • logs
  • monitoring
  • recent activity
  • dependency information
  • infrastructure configuration
  • application references

The more evidence you have, the less you're relying on guesswork.

A few common examples

Snapshots and backups

Don't delete a snapshot just because it is old.

First check whether it is a meaningful rollback point, part of a recovery process, or required by your retention policy.

EBS volumes / data disks

If an instance is gone, that does not automatically mean every attached volume is safe to delete.

Confirm the volume is no longer needed, check whether anything still references it, and make sure you know what data you are removing.

Stopped or idle EC2 instances

Stopping an EC2 instance stops instance-usage charges, but EBS storage and other billable resources associated with it can remain. AWS also charges for public IPv4 addresses. AWS EC2 documentation

So "stopped" is not the same thing as "nothing here costs money."

At the same time, that doesn't mean the right answer is always "terminate it."

The right answer depends on the business dependency and recovery plan.

Trials or automatic renewals

These are not always deletion problems.

Sometimes the right action is to disable, downgrade, or cancel a service rather than delete a resource.

Again, the question is not simply:

Is this costing money?

It is:

What exactly is costing money, and what happens if I turn it off?

The rule I keep coming back to

Cloud cost cleanup is not just a detection problem.

It's a decision problem.

Finding a resource that looks wasteful is relatively easy.

Being confident enough to remove it is harder.

That's the part I care about when I build CloudSaver.
